2. Where the CPU goes
   Split at step 5 (K): node 53.9% / postgres 46.1% of 78.7% box CPU, 500.1 rps achieved
     postgres CPU per request = 0.787 * 0.461 / 500.1 = 0.725 ms
     node     CPU per request = 0.787 * 0.539 / 500.1 = 0.848 ms
   Postgres statement execution per request (Q), excluding advisory-lock wait (sleep, not CPU):
     sum total_ms (leaderboard, both INSERTs, UPDATE, SELECT other, BEGIN, COMMIT) = 31,271.879 ms
     requests = 180,654 leaderboard + 45,715 report = 226,369
     => 0.138 ms/request executing; 0.725 - 0.138 = 0.587 ms (81%) of postgres CPU per request
        is spent outside statement execution (protocol, parse/plan, txn start/commit, wakeups).
   Round trips (Q calls):
     report statements = 45,715 BEGIN + 45,715 lock + 45,715 INSERT + 45,273 SELECT
                       + 22,636 INSERT result + 22,636 UPDATE + 45,715 COMMIT = 273,405
                       => 273,405 / 45,715 = 5.98 round trips per report
     all = 273,405 + 180,654 = 454,059 => 2.006 per request; reports cause 60.2% of them
       while being 20.2% of requests.
   Node (NP): busy 33.0 s of 92.8 s wall
     pg client stack (pg 6.58 + pg-protocol 3.56 + pg-pool 0.82 + pg-types 0.46) = 11.42 s = 34.6%
       of which socket writev from pg submit = 2.27 s
     fastify 7.02 s = 21.3% (incl. HTTP response writev 3.06 s)
     logging (pino 1.34 + sonic-boom 2.13) = 3.47 s = 10.5%

3. Conclusion
   First bottleneck: the single vCPU. The largest piece of avoidable CPU is per-round-trip
   overhead, on both sides of the socket, and ~60% of round trips come from the 6-statement
   report transaction.
